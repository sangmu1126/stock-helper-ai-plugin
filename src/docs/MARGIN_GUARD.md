# 신용거래 반대매매 가드 (Safe Trade Rule Builder 확장)

문서 버전: 1.0 · 기준일: 2026-11-18 · 상태: 구현·테스트 완료
구현: `src/skills/safe-trade-rule-builder/scripts/margin_guard.py`, `margin_check.py`, 규칙 `config/margin_rules.json`
테스트: `tests/test_margin_guard.py` (35개)

## 1. 한 문장

**신용으로 투자하는 카카오페이증권 고객이 반대매매를 피하려는데, 기준(140% 유지·120% 긴급·D+1/D+2·한시 유예)이 상담 과정에서도 틀릴 만큼 복잡해 언제·얼마를 넣어야 하는지 모른다. 이 기능은 필요한 입금액·기한·유예 여부를 출처와 함께 계산하고, 신용 매수 전에는 반대매매 구간을 먼저 보여준다.**

기존 Safe Trade Rule Builder의 약점은 "감정적 매매"가 카카오페이증권 고객의 문제라는 직접 근거가 없다는 점이었다. 이 확장은 회사 공시·공지·보도로 확인되는 고객 문제에 기존 파이프라인(파서 → 정책 → 결정)을 연결한다.

## 3. 기능

| 기능 | 입력 | 출력 | 결정 |
| --- | --- | --- | --- |
| 신용 매수 사전 점검 | "신용으로 ~ 매수" 의도 (+ 선택: 계좌) | 시작 담보비율, 140%·120%까지 하락률, 확인 질문 | `REQUIRE_CLARIFICATION` (기존 정책 엔진 경유) |
| 담보 점검 | 계좌 스냅샷 | 상태, 140% 회복 입금액/상환액, 기한·반대매매 예정일, 유예 판정 | 종료 코드 1 = 담보부족/긴급 |
| 담보비율 알림 | "담보비율 N% 아래로 내려가면 알려줘" | `notify_only` 룰, 계좌가 있으면 현재 평가 | `NOTIFY` / `WAIT` |
| 규칙 설명·오해 교정 | "120%만 맞추면 되지?" | 규칙 요약, 오해 교정 | — |

### 오안내 사례를 본뜬 시연 (가상 계좌)

| 시점 | 담보비율 | 이 기능의 안내 |
| --- | --- | --- |
| 하락 직후 | 112.0% (긴급) | 오늘 140%까지 채워야 함: 입금 1억 4,000만 원 또는 상환 1억 원. 아니면 다음 날 반대매매 |
| "120%만 넘기면 된다"고 믿고 7,600만 원 입금 | 127.2% (담보부족) | **120%를 넘긴 것만으로는 부족.** 오늘 120% 미만이었으므로 당일 140% 의무가 남아 다음 날 반대매매 대상. 추가 6,400만 원 입금 또는 4,571만 원 상환 필요 |

그 밖의 사례:
- 기존 계좌가 145%일 때 2천만 원을 신용으로 사면 매수 즉시 139.1%(담보부족)가 된다. 이 경우 확인 질문이 그 사실부터 말한다.
- 담보부족 2회차·135% 계좌는 한시 유예 `ELIGIBLE`이다. 조건(당일 08시 130% 이상, 1회)도 함께 표시한다.
- "담보비율 150% 아래로 내려가면 알려줘"는 기존에는 종목 미상의 '주가 하락' 룰로 잘못 해석됐다. 이제는 담보비율 알림 룰로 처리한다.

## 4. 설계 원칙

- 규칙 값은 `margin_rules.json`에만 둔다. 각 값에 `source`를 달고, 출처 없는 규칙은 로드 단계에서 거부한다. 규칙이 바뀌면 이 파일과 `version`만 갱신한다.
- 공식 안내에 없는 것은 `ASSUMPTION`으로 표시하고 출력에도 드러낸다. 대상은 담보비율 계산식, 150% 주의 기준, 보증금을 현금으로 낸다는 가정이다.
- 확인되지 않은 보증금률 표(원문 레이아웃 깨짐)는 `verified: false`로 두고, 경고로 노출한다.
- 기존 `src/runtime`(정책·결정 엔진)은 수정하지 않았다. 확인 질문을 추가해 기존 정책 규칙(`has_ambiguities` → `REQUIRE_CLARIFICATION`)을 그대로 쓴다.
- 투자 권유 금지 원칙을 유지한다. 어떤 종목을 팔지, 신용을 쓸지 말지는 말하지 않는다. 숫자와 기한만 제시한다.

## 5. 한계

- 실제 계좌 데이터 연동 API가 없어 계좌 스냅샷을 사용자가 입력하거나 기존 provider 인터페이스로 받아야 한다.
- 담보비율 계산식은 업계 일반식이라 앱 표시값과 다를 수 있다. 출력에 "앱 표시가 우선"이라고 항상 쓴다.
- 영업일은 주말과 입력한 휴일만 제외한다. 실제 마감 시각(입금 인정 시각 등)은 반영하지 않는다.
- 보증금을 대용으로 채우는 경우, 그리고 종목군별 정확한 보증금률은 원문 재확인이 필요하다.
- "120% 미만이 된 날은 당일 140% 회복 의무가 남는다"는 판단은 회사 안내 문구를 해석한 것이다. 출력에도 그렇게 표시한다.

## 6. 함께 고친 기존 버그

`scripts/runtime_bridge.py`가 `src/runtime`을 `sys.path` 맨 앞에 넣어, 같은 이름의 모듈(`prompt_security` 등)이 런타임 쪽으로 잘못 import됐다. 그 결과 `PYTHONPATH=src/runtime` 없이는 README의 CLI 예시와 테스트 수집이 실패했다. 이제 브리지가 스킬 스크립트 다음 순서에 런타임을 넣는다. CI 방식과 `PYTHONPATH` 없는 방식 모두에서 전체 테스트가 통과한다(작성 시점 191개).
